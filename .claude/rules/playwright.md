# Playwright 검사 규칙

브라우저로 직접 시나리오를 돌려야 할 때 (UI 회귀 확인, 통합 흐름 검증, 스크린샷 캡처) 적용한다.

## 언제 Playwright를 쓰는가

- 프론트엔드 변경 후 "실제로 동작하는지" 시각 확인이 필요할 때
- 백엔드 + 프론트 통합 흐름 (PGN 가져오기 → 분석 → 메모)
- 회귀 의심: 특정 수 네비게이션, Stockfish 캐시, 저장 후 새로고침 유지 등

타입 체크/유닛 테스트로 충분한 경우는 쓰지 않는다.

## 사전 조건

1. **백엔드 실행**: `./gradlew bootRun` (포트 8081 — `application.yml` 기준)
2. **DB 컨테이너 실행**: `docker compose up -d postgres`
3. **프론트엔드 실행**: `cd frontend && pnpm dev` (포트 5173)
4. **시작 URL**: `http://localhost:5173`

위 세 가지 중 하나라도 안 떠 있으면 시나리오 실행 전에 띄우거나 사용자에게 확인.

## 시나리오 프롬프트 골격

`docs/playwright-scenarios.md`에 시나리오별 프롬프트가 있다. 새 시나리오 작성 시 다음 7개 섹션을 채운다:

1. **목표** — 한 줄
2. **시작 상태** — URL / 로그인 필요 여부 / 사전 데이터
3. **입력** — 구체적 값 (PGN, 유저명 등)
4. **순서** — 멀티스텝 분기가 있을 때만 (1, 2, 3...)
5. **성공 조건** — 어떤 요소/텍스트/URL이 보이면 OK
6. **실패 신호** — 에러 토스트, 빈 화면, 콘솔 에러
7. **회피** — 누르지 말 것 (외부 결제, 삭제 등 — 현 앱엔 거의 없음)
8. **보고** — 스크린샷 / 콘솔 로그 / 네트워크 요청 중 필요한 것

## 진행 방식

1. 시나리오 선택 후 `browser_navigate`로 시작 URL 진입
2. `browser_snapshot`으로 접근성 트리 확인 후 다음 동작 결정
3. 단계마다 **성공 조건**과 대조 — 일치하지 않으면 멈추고 보고
4. 실패 시: 스크린샷 + 콘솔 메시지(`browser_console_messages`) + 네트워크(`browser_network_requests`) 캡처
5. 종료 시 `browser_close`로 정리

## 보고 형식

각 시나리오 종료 후 다음을 사용자에게 전달:

- **결과**: PASS / FAIL / BLOCKED
- **실패 위치**: 어느 단계에서 어떤 조건이 안 맞았는지
- **증거**: 스크린샷 경로 (`docs/test-screenshots/` 하위), 핵심 콘솔/네트워크 로그
- **추정 원인**: 한 줄

## 알려진 UI / API 사실 (시나리오 문구와 불일치할 수 있음)

시나리오 프롬프트가 다른 값을 명시해도 아래는 **현 구현 기준**으로 진행한다. 시나리오 문구를 곧이곧대로 따르려다 막히면 멈추고 사용자에게 확인.

- **가져올 경기 수 옵션**: `/import` 페이지에는 **10 / 50 / 100 / 200** 4가지 버튼만 존재. 그 외 숫자(예: "5게임")가 시나리오에 적혀 있으면 **가장 가까운 옵션(보통 10)** 으로 진행하고 보고서에 명시.
- **PGN 가져오기 API**: `GET /api/games/import?source={LICHESS|CHESS_COM}&username={name}&max={n}` — `POST`가 아니라 **GET + 쿼리스트링**. 네트워크 필터링 시 메서드 가정 주의.
