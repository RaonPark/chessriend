# Claude에게 효과적으로 요청하는 법

이 문서는 Claude가 요청을 더 정확하게 수행하기 위한 가이드입니다.

---

## 1. 어디서 작업할지 알려줘

프로젝트에 백엔드(Kotlin)와 프론트엔드(React)가 공존합니다.

**좋은 예:**
> "game 도메인의 Controller를 만들어줘"
> "프론트엔드 game feature에 게임 목록 컴포넌트 만들어줘"

**애매한 예:**
> "게임 목록 만들어줘" → 백엔드 API? 프론트 UI? 둘 다?

## 2. 레이어를 지정해줘 (백엔드)

Hexagonal 구조에서 어느 레이어를 원하는지 말해주면 정확합니다.

| 키워드 | 의미 |
|--------|------|
| "도메인" / "엔티티" | `domain/` — 순수 비즈니스 객체 |
| "유스케이스" / "서비스 로직" | `application/` — 비즈니스 흐름 |
| "포트" / "인터페이스" | `port/` — 계약 정의 |
| "컨트롤러" / "API" | `adapter/in/web/` — REST 엔드포인트 |
| "레포지토리" / "DB" | `adapter/out/persistence/` — DB 구현 |
| "클라이언트" / "외부 API" | `adapter/out/client/` — lichess, chess.com 등 |

**좋은 예:**
> "Game 도메인 엔티티를 만들어줘"
> "lichess 클라이언트 어댑터를 구현해줘"
> "게임 가져오기 유스케이스를 작성해줘"

## 3. 기능 범위를 명확하게

한 번에 전체 기능보다 단계를 나눠서 요청하면 품질이 좋아집니다.

**단계별 요청 (추천):**
> 1. "Game 도메인 엔티티를 만들어줘 (Game, Move, Position)"
> 2. "GameRepository 포트를 정의해줘"
> 3. "R2DBC로 GameRepository를 구현해줘"
> 4. "게임 목록 조회 API를 만들어줘"

**한번에 요청 (가능하지만 리뷰 어려울 수 있음):**
> "lichess에서 게임을 가져와서 DB에 저장하는 전체 흐름을 만들어줘"

## 4. 프론트엔드 요청 시 참고

프론트엔드가 익숙하지 않다면 이렇게 요청해도 됩니다:

**간단하게:**
> "체스보드를 화면에 띄워줘"
> "게임 목록을 보여주는 페이지 만들어줘"

**상세하게 (더 좋은 결과):**
> "game feature에 GameList 컴포넌트를 만들어줘. API에서 게임 목록을 가져와서 테이블로 보여줘"
> "review feature에 ReviewBoard를 만들어줘. chess.js로 수를 탐색하고 react-chessboard로 보드를 보여줘"

모르는 부분은 물어봐 주세요 — 프론트엔드 결정사항이 있으면 선택지를 드립니다.

## 5. 이런 것도 말해주면 좋아

- **"테스트도 같이"** — 테스트 코드를 함께 작성
- **"기존 코드 참고해서"** — 이미 만든 패턴을 따라감
- **"성능 괜찮아?"** — 성능 이슈를 사전에 분석
- **"다른 방법은?"** — 대안을 비교해서 제시
- **"이건 왜 이래?"** — 기존 코드나 구조를 설명

## 6. 요청 템플릿

복사해서 쓰면 됩니다:

```
[대상] 백엔드 / 프론트엔드 / 둘 다
[도메인] game / analysis / review / shared
[레이어] domain / application / port / adapter / 전체 흐름
[내용] 구체적으로 원하는 것
[참고] 추가 맥락이 있으면
```

예시:
```
[대상] 백엔드
[도메인] game
[레이어] 전체 흐름
[내용] lichess API에서 유저네임으로 최근 10게임을 PGN으로 가져와서 DB에 저장
[참고] lichess API는 NDJSON 스트리밍으로 응답함
```

## 7. 시나리오별 템플릿

위 일반 템플릿이 모든 경우에 적용되지만, 작업 종류에 따라 챙겨야 할 정보가 다릅니다.

### 7.1 새 기능 개발

자유도가 높아 결정 포인트가 많은 게 특징. **"왜"**, **참고 패턴**, **검증 기준**을 같이 적으면 결정 갈림길에서 헤매지 않습니다.

```
[목표] 한 줄 — "PGN 직접 입력으로 단일 게임 임포트"

[왜] lichess/chess.com 계정 없이도 분석하고 싶음

[범위] 백엔드 + 프론트
- 백엔드: 새 UseCase + Controller, 기존 Game 도메인 재사용
- 프론트: import 페이지에 PGN textarea 탭 추가

[제약/결정 사항]
- 중복 sourceGameId: 기존 importGames와 같이 skip
- 분석은 별도 PR

[참고할 기존 패턴]
- ImportGameUseCase / GameController.importGames
- frontend/src/features/game/components/ImportPage.tsx

[검증]
- 단일 PGN 붙여넣기 → 목록에 나타남
- 중복 PGN → 무시
- 잘못된 PGN → 에러 메시지

먼저 계획 보여주고 진행해 (Plan mode).
```

**핵심**: 미리 정해둔 건 적어주고, 안 정해진 건 "정해줘"가 아니라 "옵션 제시해줘"로.

### 7.2 버그 보고/수정

가장 어려운 시나리오. **눈으로 본 그대로** 묘사가 핵심입니다. 추상적 표현(예: "이상함", "굳어버림")보다 화면 상태(예: "흑백 50:50 + 빈 숫자")로 적어주세요.

```
[증상] 화면/동작을 구체적으로
       "변형선 진입 직후 EvalBar가 흑백 50:50으로 멈추고
        숫자가 안 보임 (또는 0.0)"

[재현 단계]
1. 게임 목록 → 분석된 게임 진입
2. 보드에서 분기점에서 d7-d5 드래그
3. EvalBar 관찰

[기대 동작] 새 포지션에 대한 라이브 평가치가 표시되어야 함
[실제 동작] 50:50 + 빈 숫자에서 안 바뀜 (또는 한참 후에야 바뀜)

[검증한 것 / 안 한 것]
- 콘솔 에러: 없음 (확인함)
- Network: 모름
- 다른 게임에서도 재현되는지: 모름

[추가 정보가 필요하면 알려줘 — Playwright/psql 등 편한 방법으로 검증해줘]
```

**핵심**:
- "굳어버린다"보다 "흑백 50:50 + 빈 숫자"가 10배 빠른 진단으로 이어집니다.
- "재현 가능 여부"가 중요. 한 번만 봤는지 매번 재현되는지에 따라 진단 방향이 완전히 달라요.
- 특정 도구(예: PostgreSQL MCP)를 지정해도 환경에 없을 수 있어요. "편한 방법으로 검증해줘"가 안전합니다.

### 7.3 UX / 리팩토링 개선

**현재 → 원하는** 형태로 차이를 명시하고, **유지할 것**을 같이 적는 게 결정적입니다.

```
[현재 동작] CommentPanel '저장' → 메모리만, 상단 '저장 (Ctrl+S)'
            또 눌러야 DB 저장 — 2단계

[원하는 동작] CommentPanel '저장' 한 번으로 DB까지

[이유] 같은 단어가 다른 동작이라 혼동

[제약 — 유지할 것]
- 우상단 '저장 (Ctrl+S)' 버튼은 변형선 저장용으로 유지
- 자동 저장(debounce) 아님 — 명시적 클릭

[테스트] 기존 CommentPanel.test.tsx 회귀 없도록
```

**핵심**: 유지할 것을 안 적으면 의도치 않게 다른 부분도 같이 손대는 경우가 생깁니다. "메모 즉시 저장"만 들으면 상단 버튼도 제거할지 고민하게 돼요.

### 7.4 검증 / 리뷰 요청

검증 깊이와 관점을 한정. 안 그러면 "괜찮아 보임"으로 끝나거나, 반대로 모든 줄에 코멘트가 달려요. (참고: `/code-review` 스킬도 이 형태)

```
[대상] feat/memo_save 브랜치, 백엔드 어댑터 + 프론트 메모 UI

[관점] 다음 순서로 봐줘
1. 헥사고날 의존 방향 위반 없는지 (도메인→어댑터로 흐르지 않게)
2. R2DBC suspend / await 누락
3. 프론트엔드 메모리 누수 / stale closure

[하지 말 것] 스타일 / 네이밍 코멘트는 생략

[출력] 발견된 이슈 우선순위(high/med/low) + 파일:줄
```

## 8. 좋은 프롬프트 vs 아쉬운 프롬프트

실제 케이스 회고:

| 케이스 | 잘 된 점 | 아쉬운 점 |
|---|---|---|
| 메모 저장 안 됨 | "DB 직접 확인하라" — 검증 의지 명확 | 지정한 도구(MCP)가 환경에 없었음, "어떻게 확인했길래 저장 안 됐다고 판단했는지" 누락 |
| CommentPanel UX 개선 | 한 줄로 의도 명확, 잘 풀렸음 | (없음) |
| EvalBar 굳음 | 정확한 묘사로 좁혀짐 | 처음에 "평가치가 안 보임"으로 시작 — "흑백 50:50 + 빈 숫자"가 첫 메시지였다면 1턴에 끝났을 것 |

---

## 9. 가장 압축한 한 줄 팁

- **새 기능**: 참고할 기존 파일 1개를 같이 적기 ("Game 도메인처럼 만들어줘")
- **버그**: 눈으로 본 그대로 묘사 ("화면이 이상함" ❌ → "EvalBar 50:50 + 0.0" ✅)
- **개선**: 유지할 것을 같이 적기
- **검증**: 봐줄 관점을 한정하기

공통: 한국어로 자연스럽게 적고, 결정 못한 건 "옵션 줘"라고 적기. 헥사고날 레이어 키워드(도메인/유스케이스/포트/어댑터)는 즉시 그 위치로 들어가게 합니다.
